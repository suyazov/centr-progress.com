## 1. Префиксный поиск «тепл», «тепло», «тёпл»

### Причина

`USE_LANGUAGE_GUESS=Y` включает определение языка запроса, но не превращает запрос в префиксный. Штатный поисковый индекс Bitrix хранит слова/стемы и обычный запрос сопоставляет поисковые термы; произвольный обрезанный префикс `тепл` не является гарантированным стемом или полным словом `теплопотребляющие`. В текущем include отсутствует нормализация `ё → е` и отсутствует явный trailing wildcard. Поэтому `тепл`, `тепло` и особенно вариант `тёпл` не имеют гарантированного совпадения с индексным словом `теплопотребляющие`. Это дефект семантики запроса, если полное название уже находится; переиндексация сама по себе префиксный поиск не добавит.

Перед реализацией на staging один раз подтвердить:

1. активный элемент «Теплопотребляющие установки» принадлежит инфоблоку `7` и находится полным запросом;
2. модуль `search` индексирует инфоблок `7`, а элемент присутствует в индексе;
3. текущие настройки морфологии/стемминга русского языка и минимальной длины слова;
4. `/search/index.php` использует ту же область инфоблока `7`.

Если полное название не находится, сначала исправить индексируемость/права/активность и выполнить полную переиндексацию. Если полное название находится, причина префиксных промахов подтверждена без изменения индекса.

### Безопасная целевая логика

Не менять ядро `bitrix/modules`. Добавить проектный адаптер нормализации, например `local/lib/CentrProgress/Search/PrefixQuery.php`, и подключить его в проектной копии компонента `local/components/centrprogress/search.title/` (копия штатного `bitrix:search.title` текущей установленной версии). В `bitrix/templates/template/footer.php` переключить имя компонента на `centrprogress:search.title`, сохранив текущий шаблон и параметры.

Алгоритм адаптера:

1. принять исходный `q`, ограничить длину и число токенов;
2. выполнить Unicode lowercase, заменить `ё` на `е`, схлопнуть пробелы;
3. удалить пользовательские операторы/wildcard и экранировать синтаксис поиска;
4. для кириллических/латинских токенов длиной не менее 4 символов добавить только конечный `*`; короткие токены искать штатно или отклонять по UX-правилу;
5. передать преобразованный запрос штатному `CSearch` с текущей областью `iblock_infosection/7`;
6. не делать SQL `LIKE '%...%'` по таблицам инфоблока и не отключать проверку прав.

Ожидаемое преобразование: `тепл`, `тепло`, `тёпл` → `тепл*`; полное `Теплопотребляющие установки` → `теплопотребляющие* установки*`. Нормализованный запрос нужен и быстрому компоненту, и `/search/index.php`; после возврата отсутствующего entry-point в Git подключить тот же класс перед `bitrix:search.page` либо использовать общий проектный компонент-обёртку.

Такой вариант ограничивает wildcard префиксом, сохраняет индексный поиск и контроль доступа, устраняет различие `е/ё` и не создаёт дорогой ведущий wildcard.

### Проверки

- `тепл`, `тепло`, `тёпл`, `ТЕПЛ` возвращают «Теплопотребляющие установки» в подсказке и на полной странице;
- полное название продолжает находиться;
- запросы из 1–3 букв не создают тяжёлый wildcard-запрос;
- спецсимволы, кавычки, `*`, `-`, HTML и строка чрезмерной длины безопасно нормализуются;
- результаты остаются только из инфоблока `7`, не раскрывают неактивные/недоступные элементы;
- время ответа на staging не деградирует на контрольном наборе запросов.

После изменения индексируемых данных или настроек поиска нужна полная переиндексация. После одного лишь изменения query adapter переиндексация не требуется, но нужно очистить кеш компонентов поиска и composite-кеш целевых страниц.

## 2. Файл «Образовательная программа»

### Текущее состояние

Файл относится к элементу направления обучения в инфоблоке `7`, код свойства — `PROGRAMM`. Это отдельное файловое свойство программы, не блок документов из инфоблока `20` и не общее множественное свойство `FILE`, которое сейчас выводится во вкладке «Выдаваемые документы».

Публичный код `template.php` уже обращается к `DISPLAY_PROPERTIES['PROGRAMM']['FILE_VALUE']`, то есть ожидает Bitrix-свойство типа «Файл». Но блок полностью закомментирован в обеих desktop/mobile областях шаблона; загруженный `PROGRAMM` сейчас на публичной карточке через этот код не выводится.

На staging до разработки проверить в административной части инфоблока `7`:

- название `Образовательная программа`, символьный код строго `PROGRAMM`, тип `F` («Файл»), активность;
- одиночное или множественное свойство и фактический numeric property ID;
- наличие `PROGRAMM` в `DETAIL_PROPERTY_CODE` параметров комплексного каталога на реальном entry-point;
- тестовый файл у одного элемента и отсутствие файла у второго.

### Точные изменения

1. Вернуть в Git реальный PHP entry-point комплексного каталога и добавить `PROGRAMM` в его `DETAIL_PROPERTY_CODE`. Не хардкодить numeric property ID.
2. В `bitrix/templates/template/components/bitrix/catalog/catalog/bitrix/catalog.element/.default/template.php` заменить оба закомментированных фрагмента единым выводом (лучше вынести в `parts/EducationProgram.php` и подключить из mobile/desktop позиции без дублирования).
3. Строить данные через `DISPLAY_PROPERTIES['PROGRAMM']['FILE_VALUE']`; поддержать одиночное и множественное значение. Для каждого валидного файла требовать непустой `SRC`; подпись ссылки — `Образовательная программа` (или описание файла, если продукт явно выберет его), атрибут `download` не навязывать для внешних URL. Размер показывать только если `FILE_SIZE > 0`.
4. Весь контейнер рендерить только при наличии хотя бы одного валидного файла. При пустом, удалённом или недоступном значении не выводить заголовок, разделитель, размер и пустой `.Files`.
5. URL и подпись экранировать штатными средствами Bitrix/`htmlspecialcharsbx`; не собирать путь из имени файла.

Кеш `bitrix:catalog.element` сейчас в комплексном шаблоне принудительно задан как `CACHE_TYPE=N`, однако composite/page cache может сохранить HTML. После изменения шаблона очистить только кеш компонента/страницы на staging; загрузка или удаление свойства должна инвалидировать managed cache инфоблока, если на реальном окружении компонент вернут к автоматическому кешу.

### Проверки

- одиночный PDF: видна одна ссылка «Образовательная программа», URL отдаёт файл, размер корректен;
- несколько файлов: каждый доступен, порядок соответствует значениям свойства;
- свойство пусто: нет текста и пустого контейнера;
- файл удалён/`SRC` пуст: битая ссылка не выводится;
- имена и описания со спецсимволами не ломают HTML;
- desktop и mobile не дают двух видимых копий одновременно.

## 3. Сортировка направлений через «Сорт.»

### Причина и целевая логика

Административное поле элемента «Сорт.» — стандартное поле `SORT`. Шаблон списка не меняет порядок, но `section.php` передаёт неопределённые `$sort/$sort_order`; кроме того, вторичная сортировка повторяет первичную. Это не даёт проверяемого контракта и не обеспечивает детерминированный порядок элементов с одинаковым `SORT`.

В `bitrix/templates/template/components/bitrix/catalog/catalog/section.php` для публичного `bitrix:catalog.section` задать явно:

```php
"ELEMENT_SORT_FIELD" => "sort",
"ELEMENT_SORT_ORDER" => "asc",
"ELEMENT_SORT_FIELD2" => "id",
"ELEMENT_SORT_ORDER2" => "asc",
```

В реальном entry-point комплексного каталога также установить эти четыре параметра, чтобы его search/other list routes получали тот же контракт. В `bitrix/templates/template/components/bitrix/catalog/catalog/search.php` параметры уже пробрасываются без переопределения; после фикса entry-point поиск каталога будет сортироваться одинаково.

Отдельно применить `SORT ASC, ID ASC` к каждому публичному вызову, который действительно показывает направления инфоблока `7`. Подтверждённый основной вызов — `catalog/catalog/section.php`; `related` на карточке не является основным списком и требует отдельного продуктового решения, поскольку сейчас там также используются неопределённые переменные. Сортировка разделов уже использует `CIBlockSection::GetList(['SORT' => 'ASC'])`, но для полной детерминированности должна быть `['SORT' => 'ASC', 'ID' => 'ASC']`, если требование распространяется и на разделы.

Не сортировать `arResult.ITEMS` в PHP-шаблоне: это ломает пагинацию и кеш-ключ. Администратор меняет порядок штатным полем «Сорт.» элемента; меньшие значения выводятся раньше, равные — по меньшему `ID`.

### Проверки

- элементы с `SORT` 100, 200, 300 выводятся именно в этом порядке;
- после изменения «Сорт.» 300 → 50 элемент становится первым после очистки/инвалидации кеша;
- элементы с одинаковым `SORT` стабильно идут по `ID ASC` на разных страницах пагинации;
- фильтр, переход между разделами и полная страница поиска не меняют правило;
- неактивные элементы и элементы вне выбранного раздела не появляются.

После изменения только поля `SORT` переиндексация поиска не нужна. Нужна штатная инвалидация managed cache инфоблока; при старом/нестандартном кеше — адресная очистка кеша каталога и composite-кеша на staging.

## План реализации и приёмки

1. Активировать capability из следующего раздела и получить изолированный staging.
2. Вернуть в Git отсутствующие entry-points `/search/index.php` и комплексного каталога без секретов/сгенерированного кеша.
3. Read-only проверить метаданные инфоблока `7`, свойства `PROGRAMM`, настройки search и контрольный элемент; записать numeric ID только как evidence, не использовать его в коде.
4. Реализовать общий prefix adapter и подключить быстрый и полный поиск.
5. Включить условный безопасный вывод `PROGRAMM` и явную сортировку `SORT ASC, ID ASC`.
6. Запустить PHP lint изменённых PHP-файлов, unit/fixture тест нормализатора, затем один staging smoke по тест-кейсам выше.
7. Выполнить адресную очистку кеша; полную переиндексацию запускать только если preflight выявил проблему индекса/настроек или менялись индексируемые данные.
8. Доставка только на staging через Bridge receipt; production остаётся отдельным ручным решением.

## Product capability prerequisite

Текущий repository policy — `docs-only`, delivery disabled, production false. До любого изменения PHP/Bitrix или среды Bridge должен активировать отдельный безопасный профиль `product` для 1C-Bitrix/PHP со следующими свойствами:

- изолированное non-production staging `centr-progress.com-staging`, не обслуживающее production-трафик, с той же поддерживаемой версией Bitrix/PHP и обезличенной либо минимальной тестовой БД;
- разрешённые application paths только для согласованных `local/**`, шаблонов `bitrix/templates/template/**` и возвращённых в Git entry-points; запрет на `bitrix/modules/**`, upload, credentials, DNS и production configuration;
- read-only preflight схемы инфоблока `7`, свойства `PROGRAMM` и search settings без вывода данных/секретов; любые DB-изменения — только отдельной явной миграцией на staging с backup/rollback;
- PHP lint версией, совместимой с target runtime, автоматический тест нормализатора и bounded HTTP smoke для поиска, карточки и сортировки;
- отдельный environment lock, scoped deploy из точного reviewed merge SHA, адресная очистка кеша и управляемая переиндексация только при доказанной необходимости;
- durable Deployment Receipt с `environment=staging`, точным source/merge SHA, результатами проверок и `production_touched=false`, затем live verification staging URL;
- merge/deploy выполняет Bridge policy после review; managed Codex не пушит `main`, не merge и не касается production. Production delivery/DNS требуют новой явной авторизации и не входят в этот capability.

Без этого профиля следующий допустимый статус — документация готова, product implementation blocked by capability prerequisite.
